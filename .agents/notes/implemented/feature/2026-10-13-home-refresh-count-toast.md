# Agent Note: 首页手动刷新新内容计数 Toast

Status: implemented

## Problem

首页点击刷新后没有反馈实际加载了多少新的或更新过的话题。网页端的提示语对应的是刷新结果中的新话题或内容更新，而不是当前列表总长度。

## Decision

在首页 Feed 的每次成功手动刷新中，将刷新接口返回的话题与上次成功加载的首页基线按话题 ID 比较。新出现的话题和可见内容字段发生变化的话题各计一次，结果通过 ViewModel 一次性事件传给首页 Snackbar，显示“已为你加载 N 条新内容”。初次加载、后台探测、分页和账号切换不发送该事件。分类和标签页复用同一 ViewModel，但不发送首页事件。

## Alternatives considered

- 直接使用刷新响应当前页的总条数：实现简单，但会把未新增的已有话题重复算入提示，和网页端语义不符。
- 仅依赖 MessageBus 推送计数：推送只适合产生待刷新提示，不能确认手动刷新接口实际返回的结果，也无法覆盖推送缺失的情况。

## Consequences

- 手动刷新成功后发送一次事件，数量来自本次刷新接口返回与旧基线的比较。
- 没有新话题或内容更新时也发送 0，失败时不发送成功提示。
- 初次加载、后台探测和分页不会产生首页刷新 Toast。
- 有单元测试覆盖新增、更新、无变化和失败场景，并通过笔记校验。

刷新接口只返回当前页时，已经被新话题挤出当前页的旧话题无法参与比较；计数范围因此与接口返回页一致，这是服务端分页边界的限制。手动刷新即使没有变化也发送 0，便于 UI 明确反馈请求已完成。

## Testing

`FeedViewModelTest.manualRefreshReportsNewAndUpdatedTopicsFromTheResponse` 覆盖一个更新话题和一个新话题被计为 2；首次加载不触发事件。后续首页 Snackbar 测试覆盖事件文案与消费。
